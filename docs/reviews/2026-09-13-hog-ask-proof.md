# `hog_ask`: accepted working proof

**Disposition:** structural previews and recorded runtime proof approved. After
receiving this proof, Ondrej replied "ok I think thats fine", with no revisions
requested. Implementation source: `8d14ba5`. That acceptance alone did not
authorize publishing or profile activation. A subsequent explicit request
authorized both: the immutable 0.2.3 release is now activated locally and verified,
while npm publication awaits authentication. See the [activation record](../plans/2026-09-13-fix-pi-question-interaction-plan.md#authorized-local-activation--npm-publication-blocked).
This is one card, not a questionnaire system.

## What ran

Pi **0.85.1**, real offline CLI, temporary profiles outside the repository. The
benign fixture wraps the actual package entrypoint and invokes its registered
`hog_ask` definition. No model, credentialed service, selected command, deployment
or publishing operation is called. The demonstration's approval scope expressly
permits only recording a demo answer.

- **PTY, regular and fullscreen:** decision → custom answer → optional note →
  review → Send; approval → qualifying note → discussion result; resize from
  80×40 to 36×24; long-scope navigation and dismissal. Actual terminal output was
  decoded with pyte, not generated by calling the renderer directly.
- **RPC:** real standard select/input requests; an approve selection plus
  “yes, but only after a dry run” returned `needs_discussion`, `approved: false`,
  retaining the option ID and note. Cancelling a custom-answer input returned
  `dismissed`, no answer, no approval, and no model turn.
- **Isolated discovery:** standalone package, skills-only configuration and the
  existing sibling workstation `/answer` all loaded without duplicate launchers
  or load errors. No live configuration was changed.

Reproduce from the source checkout:

```sh
node --test tests/pi-hog-ask*.test.mjs tests/pi-rpc-smoke.test.mjs
uv run scripts/pi-hog-ask-proof.py --output /tmp/hog-ask-proof
```

Use `PI_BIN` to select the runtime. The optional combined-profile test accepts
`HOG_TEST_WORKSTATION_ANSWER=/path/to/answer.ts` and explicitly skips if unavailable.
The PTY script requires a POSIX PTY and uv; its pyte dependency stays in uv's cache.
Both proof helpers are development-only and excluded from the published package.

## Terminal excerpts

These are excerpts of captured terminal screens, not replacement design sketches.
Unrelated startup warnings and filesystem/footer lines are omitted. Full local
captures are written under `/tmp/hog-ask-proof/` by the command above.

### Decision, before any selection

```text
Decision: Rollout audience (demo)
Who should have access first?
Demonstration only. No implementation, publishing or deployment will run.
Recommended: Internal only — A smaller pilot reduces risk.

No option selected. Review before sending.
> ( ) Internal only [recommended]
    Validate with support before wider exposure.
  ( ) Public
    Wider reach and greater rollout risk.
  Write a different answer
  Dismiss

up/down navigate · enter choose · escape/ctrl+c dismiss
```

`>` means keyboard focus; `( )` is still empty. Selecting an option opens review.
Review initially focuses Back, so repeated Enter does not submit approval.

### Qualified approval, after editing its note

```text
Approval: Record a demo approval
Approve only this demonstration scope?
Demonstration only. No implementation, publishing or deployment will run.
Scope: Record this demo answer only. No real-world operation is authorized.
Artifact: demo/plan.md
Revision: demo-r1

Review answer — not yet submitted
Answer: Approve this scope
Note: yes, but dry run first
Approve only the named action and scope.
No approval granted: this answer needs discussion.

> Back / change answer
  Add / edit note
  Send answer
  Dismiss
```

Sending this records the qualification, **not approval**. Custom approval text has
the same conservative meaning; no heuristic decides which notes are harmless.

## RPC equivalent

The client received the entire question, scope, artifact and revision on each
step. Review's explicit actions were:

```text
Action: Back / change answer
Action: Add / edit note
Action: Send answer
Action: Dismiss
```

The qualifying-note result contained:

```json
{
  "status": "needs_discussion",
  "approved": false,
  "answer": {
    "kind": "option",
    "optionId": "approve",
    "label": "Approve this scope",
    "note": "yes, but only after a dry run"
  }
}
```

The actual result also includes the normalized question/scope, origin session/leaf
and readable Q&A. RPC input layout belongs to the client; it may be single-line.
Standard abortable input replaces the proposed RPC editor because Pi 0.85.1's
editor request has no AbortSignal support.

## Findings addressed and evidence limits

- Native Editor displays collapsed paste markers: saving now uses expanded text,
  with a regression asserting the original full pasted answer.
- Long cards need a bounded scroll viewport, including the last help line.
  Unicode width, resize, long scope/review and fullscreen arrow access are tested.
- After editing, review resets to neutral Back rather than leaving focus on Send.
- Abort/disposal closes once; stale success/rejection cannot approve or release a
  newer owner's lock. RPC input/select both receive the cancellation signal.
- An independent read-only review session was interrupted before returning a
  verdict; it is **not** counted as a completed independent approval. Parent
  review, focused tests and real runtime proofs are the recorded evidence.

Automated fixtures do not prove the model will always ask the right question,
that every RPC client renders well, or that this feels comfortable to Ondrej.
Ondrej accepted this recorded proof; that satisfies the feedback gate, not a
claim of hands-on usability testing. Subsequent activation used a new immutable
release; the previous release's files remain unchanged. Fresh sessions load the
new source; already-open sessions need `/reload`. npm publication is still
blocked by authentication. Source push alone is not activation.
